K8s1小白初体验——接触概念、集群初始化与 containerd 配置

2026.09.22 大三上学期

终于来到 k8s 了，也就是Kubernetes。记得老师说，Kubernetes这个单词，字母太多了，中间有8个字母，就简记为k8s了。下面，我们走进它，一起看看它的应用。

一、 K8s 基础概念与组件

(1) 理解

1. K8s 是什么

K8s，全名 Kubernetes，是一个管理容器的工具，严谨一点，可以称之为 容器编排平台。

之前学习的 Docker ，可以理解为，把应用装进了“集装箱”，而 K8s ，就是来管理这些集装箱的。K8s 可以决定它们放哪里，跑几个，坏了怎么办。

具体地，K8s 会帮我们做：自动部署应用、自动扩缩容、容器挂了自动拉起来、服务发现（让 Pod 之间能通过名字找到彼此）、负载均衡（将流量分给多个 Pod）、滚动更新回滚。

哇，这样听起来，和 Docker Swarm 很像呢。

Docker 和 k8s 是相互配合使用的，但 Docker 只管单个容器， K8s 会管理整个集群的很多荣去。

2. K8s 集群

K8s 集群一般有两类机器，Master / Control Plane 控制平面 和 Worker / Node 工作节点。

在 Master 上，有四个核心组件：

  1. kube-apiserver：这是 K8s 的唯一入口，也是唯一直接和etcd对接的组件，像公司的前台 + 总机。

  2. etcd：这是 K8s 的数据库，储存着所有集群的状态（Pod、Service、节点信息、配置等），像K8s的账本。

  3. kube-scheduler：它可以给新Pod选节点，它会找出合适的节点，并选最高分节点绑定Pod，是调度员。

  4. kube-controller-manager：它会运行各种控制器，发现节点挂了、Pod少了，会自动修复，像一群管家。

在 Worker 上，有三个核心组件：

  1. kubelet：它会接收Master下发的Pod信息，并执行相关操作，“领导说这个 Pod 要跑，我来让它跑起来。”

  2. kube-proxy：它是节点上的网络代理，负责维护网络规则，实现k8s的service，让集群内外可以访问Pod。

  3. 容器运行时：这个听着很不像一个组件名呀，没事，不要有母语羞耻（bushi）。这就像发动机，真正负责运行容器的软件，K8s 下命令，它真正来启动容器。常见的有：containerd、CRI-O、Docker。

3. 两个常见插件

  1. CoreDNS：
    就和DNS解析相关的，他是集群内的DNS服务器。可以把Service名字解析成IP，让Pod可以通过服务器名访问其他的服务。

  2. Calico：
    这是网络插件（CNI插件），给每个Pod分配唯一的IP，让不同节点上的 Pod 能互相通信。

二、 创建一个 Pod

(1) 理解

Pod是k8s的最小管理单元，那么到底要怎么创建一个Pod呢？我们大致分为下面 5 步。

  1. 敲 kubectl，告诉 apiserver：我要一个 Pod。

  2. apiserver 把 Pod 信息写进 etcd（记账）。

  3. scheduler 看到新 Pod，选一台节点，比如 k8s2。

  4. kubelet 收到通知，让 containerd 把容器跑起来。

  5. Calico 给 Pod 发 IP，kubelet 把状态回报给 apiserver。

这就像是，我们“下单 → 记账 → 调度 → 干活 → 汇报”。

我们通过一个简单的实验，具体理解一下创建Pod的过程。

(2) 实验

我们计划创建一个 test-pod ，里面放一个容器，用 Harbor 现成的镜像。

1. 检查集群环境

[root@k8s1 ~]# kubectl get nodes
NAME   STATUS   ROLES           AGE   VERSION
k8s1   Ready    control-plane   11d   v1.35.8
k8s2   Ready    worker          11d   v1.35.8

嗯……因为之前已经实验过了，我的集群状态是好的，两个节点都是Ready。

2. 创建 Pod 文件

我们先写一个 Pod 文件。

[root@k8s1 ~]# cat <<EOF > test-pod.yaml
> apiVersion: v1
kind: Pod
metadata:
  name: test-pod
spec:
  containers:
  - name: pause
    image: reg.westos.org/k8s/pause:3.10.1
> EOF
[root@k8s1 ~]# cat 简单YAML.txt
apiVersion: v1          # 用哪套 API（K8s 固定几个值）
kind: Pod               # 我要创建什么（Pod / Service / Deployment...）
metadata:               # 这张表的“基本信息”
  name: shared-pod      #   名字叫啥
spec:                   # 这张表的“详细要求”
  containers: ...       #   具体怎么跑

这里有一个简单的模板，对应地，我们的 test-pod.yaml 文件创建的这个 Pod ，里面只有 pause 一个容器，用的是 Harbor 里 k8s 项目的 pause 镜像。

3. 创建 Pod，查看状况

我们把 test-pod.yaml 交给 apiserver，apiserver 会写进 etcd。

[root@k8s1 ~]# kubectl apply -f test-pod.yaml
pod/test-pod created
[root@k8s1 ~]# kubectl get pods -o wide
NAME       READY   STATUS    RESTARTS   AGE   IP              NODE   NOMINATED NODE   READINESS GATES
test-pod   1/1     Running   0          23s   10.244.109.99   k8s2   <none>           <none>

此时，Pod 已经跑起来了（running），Calico 分配的 Pod IP 是 10.244.109.99 （IP = 10.244.109.99），scheduler 把它调度到了 k8s2（NODE = k8s2）。

4. 查看调度情况

它具体是怎么被调度的呢？

[root@k8s1 ~]# kubectl describe pod test-pod
Name:             test-pod
Namespace:        default
# ... ... ... ()
Events:
  Type    Reason     Age    From               Message
  ----    ------     ----   ----               -------
  Normal  Scheduled  4m58s  default-scheduler  Successfully assigned default/test-pod to k8s2
  Normal  Pulled     4m56s  kubelet            spec.containers{pause}: Container image "reg.westos.org/k8s/pause:3.10.1" already present on machine and can be accessed by the pod
  Normal  Created    4m56s  kubelet            spec.containers{pause}: Container created
  Normal  Started    4m56s  kubelet            spec.containers{pause}: Container started

我们只看最后的 Events 部分，四行过程如下。

  1. Scheduled：scheduler 选了 k8s2。

  2. Pulling：k8s2 上的 kubelet 让 containerd 拉镜像，Pulled：镜像拉好了。

  3. Created：容器创建了。

  4. Started：容器启动了。

三、 集群环境初始化

(1) 理解

其实没什么需要理解的，就是部署一个集群而已（bushi… …）。

在此处分享一下 k8s 的官网链接 Kubernetes 文档 | Kubernetes ，有需要的话，可以跟着官网的步骤一步步来。

(2) 实验

对于每台 K8s 节点，都需要我们做一些基础的配置。

1. 检查 swap 和时间

如果节点上，Swap 行都是 0B ，这就表明 Swap 已经关闭了。

[root@k8s1 ~]# free -h
               total        used        free      shared  buff/cache   available
Mem:           3.5Gi       1.2Gi       1.4Gi        10Mi       1.2Gi       2.4Gi
Swap:             0B          0B          0B

如果数字不为零，就需要关一下。

swapoff -a
sed -i '/swap/s/^/#/' /etc/fstab

K8s 为了保证 Pod 性能稳定，不允许内存被换出到磁盘。

检查时间同步，看一下 timedatectl 命令下，我的 System clock synchronized 是 yes ，可以不用再执行了。但如果是 no ，就需要同步一下时间。

dnf install -y chrony
systemctl enable --now chronyd
chronyc sources -v

生产集群节点多，时间差超过几秒，证书和日志就会乱套。

2. 检查 SELinux 和防火墙

检查当前集群的状态。

[root@k8s1 ~]# getenforce
Disabled
[root@k8s1 ~]# systemctl is-active firewalld.service
inactive

这是对哒，防火墙关闭。那如果不对的话，就要执行下面的操作。

setenforce 0
sed -i 's/^SELINUX=enforcing/SELINUX=disabled/' /etc/selinux/config 

systemctl stop firewalld
systemctl disable firewalld

3. 补内核参数和系统限制

创建 /etc/sysctl.d/k8s.conf 文件，写入 ip_forward=1 和 bridge-nf-call-iptables=1 ，使 Pod 允许 IP 转发，并让网桥流量走 iptables （Service 转发需要）。

[root@k8s1 ~]# cat /etc/sysctl.d/k8s.conf
net.ipv4.ip_forward = 1
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
[root@k8s1 ~]# sysctl --system
* Applying /usr/lib/sysctl.d/10-default-yama-scope.conf ...
# ... ... ...()
[root@k8s1 ~]# sysctl net.ipv4.ip_forward
net.ipv4.ip_forward = 1
[root@k8s1 ~]# sysctl net.bridge.bridge-nf-call-iptables
net.bridge.bridge-nf-call-iptables = 1

不配内核参数的话，Pod 可能无法跨节点通信，Service 无法负载均衡。

继续补上系统限制。

[root@k8s1 ~]# cat /etc/security/limits.conf
# /etc/security/limits.conf
# ... ... ...()
# End of file
* soft nofile  65536
* hard nofile  65536
* soft nproc  65536
* hard nproc  65536
* soft memlock unlimited
* hard memlock unlimited

在 etc/security/limits.conf 文件最后，追加上面几行内容（从* soft nofile 到 * hard memlock unlimited）。

nofile 限制一个进程最多打开的文件数，nproc 限制一个用户最多打开的进程数， memlock unlimited 允许锁定内存， etcd 会需要。

4. 安装 IPVS 依赖

我已经做过初始化了，这里把命令说明一下就好。

dnf install -y ipset ipvsadm 
cat <<EOF > /etc/modules-load.d/ipvs.conf
ip_vs
ip_vs_rr
ip_vs_wrr
ip_vs_sh
nf_conntrack
EOF 
systemctl restart systemd-modules-load.service 
# 验证：lsmod | grep -e ip_vs -e nf_conntrack

我们安装 ipset 、 ipvsadm ，加载了 ip_vs 等模块。

kube-proxy 默认用 iptables，但在大规模集群里，IPVS 性能更好、转发更快（生产环境几千个 Service，iptables 会卡爆，还是得用 IPVS）。

四、 部署 containerd

(1) 理解

想要启动容器，就要把 containerd 运行所需要的基础设施搭建好，其实也就是四个模块。在这里介绍一下四个模块的作用。

模块 用途 比喻 商场里的什么？
overlay 让容器内部的文件系统叠加在宿主机上 📂 像文件夹套娃，一层叠一层 仓库系统（货物统一管理）
br_netfilter 让容器能桥接网络、进行网络过滤 🌐 容器之间的”网络交换机” 商场大门 + 通道
nf_conntrack 追踪网络连接状态（NAT、负载均衡） 📝 记录谁连了谁 顾客登记系统（谁来了）
ip_tables 防火墙规则（iptables） 🚧 控制网络流量进出 安保 / 门禁规则

这些模块默认可能没有开启， containerd/Docker 又需要用到它们，就需要我们手动加载。

(2) 实验

1. 加载依赖内核模块

我们要在 k8s1 和 k8s2 上创建 conf 文件，把四个模块名写进去。

[root@k8s1 ~]# cat /etc/modules-load.d/containerd.conf
overlay
br_netfilter
nf_conntrack
ip_tables
[root@k8s1 ~]# systemctl restart systemd-modules-load.service

这样，systemd 开机时会读取 /etc/modules-load.d/ 下的 .conf 文件，自动加载里面的模块。

2. 安装 containerd.io 和 cri-tools

我已经安装过啦，把命令在这里贴出来就好。

dnf install -y containerd.io cri-tools

可以通过查看版本号（xx –version），验证一下。

[root@k8s1 ~]# rpm -qa | grep -E 'containerd.io|cri-tools'
containerd --version
crictl --version
containerd.io-1.6.33-3.1.el7.x86_64
cri-tools-1.35.0-150500.1.1.x86_64
containerd containerd.io 1.6.33 d2d58213f83a351ca8f528a95fbd145f5654e957
crictl version v1.35.0
[root@k8s2 ~]# rpm -qa | grep -E 'containerd.io|cri-tools'
containerd --version
crictl --version
cri-tools-1.35.0-150500.1.1.x86_64
containerd github.com/containerd/containerd/v2 2.2.7 1.el9
crictl version v1.35.0

我 k8s1 和 k8s2 上的版本不一样，但并不太影响实验。

3. 修改 containerd 配置

我们让 containerd 自己生成默认的配置文件，保存在 /etc/containerd/config.toml 里。

containerd config default > /etc/containerd/config.toml 
sed -i 's/SystemdCgroup = false/SystemdCgroup = true/g' /etc/containerd/config.toml 
sed -i 's#sandbox_image = ".*"#sandbox_image = "reg.westos.org/k8s/pause:3.10.1"#' /etc/containerd/config.toml 
sed -i 's#config_path = ""#config_path = "/etc/containerd/certs.d"#' /etc/containerd/config.toml 
systemctl restart containerd

我们修改了三个关键的参数。

参数 改之前 改之后 为什么
SystemdCgroup false true 和 kubelet 的 cgroup 驱动保持一致，避免资源管理冲突
sandbox_image 默认 k8s 官方地址 你的 Harbor 地址 让 Pod 的 pause 容器从你自己的仓库拉，不依赖外网
config_path 空 /etc/containerd/certs.d 告诉 containerd 私有仓库的证书放在哪

重启 containerd ，服务就可以生效了。

4. 让 containerd 连接 Harbor

首先呢，我们要有 Harbor 证书，并确保 containerd 。可以从 Harbor 服务器拷贝过来。

[root@k8s1 ~]# ls -l /etc/containerd/certs.d/reg.westos.org/ca.crt
-rw-r--r-- 1 root root 1935 Sep 10 15:08 /etc/containerd/certs.d/reg.westos.org/ca.crt
[root@k8s1 ~]# grep config_path /etc/containerd/config.toml
      config_path = "/etc/containerd/certs.d"
[root@k8s1 ~]# # scp reg.westos.org:/data/certs/westos.org.crt /etc/containerd/certs.d/reg.westos.org/ca.crt

依旧是重启生效哈。我们测试一下能否从 Harbor 拉取镜像呢？

[root@k8s1 ~]# systemctl restart containerd
systemctl is-active containerd
active
[root@k8s1 ~]# crictl pull reg.westos.org/k8s/pause:3.10.1
E0922 17:19:29.913842  105684 log.go:32] "PullImage from image service failed" err="rpc error: code = Unknown desc = failed to pull and unpack image \"reg.westos.org/k8s/pause:3.10.1\": failed to resolve reference \"reg.westos.org/k8s/pause:3.10.1\": failed to do request: Head \"https://reg.westos.org/v2/k8s/pause/manifests/3.10.1\": tls: failed to verify certificate: x509: certificate signed by unknown authority" image="reg.westos.org/k8s/pause:3.10.1"
FATA[0000] pulling image: failed to pull and unpack image "reg.westos.org/k8s/pause:3.10.1": failed to resolve reference "reg.westos.org/k8s/pause:3.10.1": failed to do request: Head "https://reg.westos.org/v2/k8s/pause/manifests/3.10.1": tls: failed to verify certificate: x509: certificate signed by unknown authority

失败了。报错信息 x509: certificate signed by unknown authority 的意思是：containerd 不相信 reg.westos.org 这个 HTTPS 站点的证书。

来到docker1上看一下 nginx 实际应用的证书。

[root@docker1 ~]# # 查看 nginx 配置中实际加载的证书路径
docker exec nginx nginx -T 2>/dev/null | grep -E 'ssl_certificate|ssl_certificate_key'
    ssl_certificate /etc/cert/server.crt;
    ssl_certificate_key /etc/cert/server.key;
[root@docker1 ~]# # 从 nginx 容器拷贝证书到宿主机临时目录
docker cp nginx:/etc/cert/server.crt /tmp/nginx-server.crt

# 检查这个证书是否是 CA 证书，并查看它的签发者与使用者
openssl x509 -in /tmp/nginx-server.crt -text -noout | grep -E "CA:|Basic Constraints|Issuer:|Subject:"
Successfully copied 1.86kB (transferred 3.58kB) to /tmp/nginx-server.crt
        Issuer: CN=reg.westos.org
        Subject: CN=reg.westos.org
            X509v3 Basic Constraints: critical
                CA:TRUE

我们的证书路径不对捏。

回到 k8s1 和 k8s2 ，用 hosts.toml 来解决证书验证的问题。（其实之前配置过一次，但路径错了，就得重新从 nginx 容器提取实际加载的证书（/etc/cert/server.crt），来替换错误的 ca.crt）

[root@k8s1 ~]# scp root@192.168.86.101:/tmp/nginx-server.crt /etc/containerd/certs.d/reg.westos.org/ca.crt
root@192.168.86.101's password:
nginx-server.crt                                                            100% 1858   178.9KB/s   00:00
[root@k8s1 ~]# cat <<EOF > /etc/containerd/certs.d/reg.westos.org/hosts.toml
server = "https://reg.westos.org"
[host."https://reg.westos.org"]
  capabilities = ["pull", "resolve", "push"]
  ca = "/etc/containerd/certs.d/reg.westos.org/ca.crt"
EOF
[root@k8s1 ~]# systemctl restart containerd
crictl pull reg.westos.org/k8s/pause:3.10.1
Image is up to date for sha256:cd073f4c5f6a8e9dc6f3125ba00cf60819cae95c1ec84a1f146ee4a9cf9e803f
[root@k8s1 ~]# crictl images | grep pause
reg.westos.org/k8s/pause                     3.10.1              cd073f4c5f6a8       318kB

恢复 hosts.toml 的 ca 配置后，重启 containerd，成功拉取镜像。

5. 配置 crictl

我们确认一下 /etc/crictl.yaml 文件，再试试 crictl 能否正常工作。

[root@k8s2 ~]# cat /etc/crictl.yaml
runtime-endpoint: unix:///run/containerd/containerd.sock
image-endpoint: unix:///run/containerd/containerd.sock
[root@k8s2 ~]# crictl info
{
  "cniconfig": {
# ... ... ...()

oh不，一下子就输出了好长好长的东西。但crictl确实是正常在工作啦。
