高可用与负载均衡-1

2026.07.24 大二集训

7/22 am

本节进入了新的一个小专题，与服务器架构相关，老师给这节课取名为”高可用与负载均衡”。我们可以新开虚拟机的环境，让实验环境是干净清晰的。

一、服务器架构与核心概念

1. 高可用（HA）与负载均衡（LB）

我们先了解一下这几个关键词吧

  • 高可用：核心目标是消除单点故障，当系统某个组件（如服务器、调度器）发生故障时，能自动切换到备用组件，保证服务不中断。最典型的实现是双机热备，分为主备模式（仅主节点工作，备节点待命）和双活模式（双节点同时处理请求，需搭配分布式文件系统如 Ceph/GFS，避免存储脑裂）。生产环境中还需配合电源控制器、直连心跳线（独立于业务网络的网卡直连，规避交换机故障风险）进一步提升可靠性。

  • 负载均衡：通过将客户端流量合理分发到多台后端服务器，解决单台服务器性能瓶颈，提升系统整体处理能力。负载均衡器本身也是单点，因此通常与高可用方案结合部署。常见调度算法包括轮询、加权轮询、最少连接、源地址哈希等。

  • CDN（内容分发网络）：现代网站的标配组件，通过全球边缘节点缓存静态内容，将用户请求就近返回，既加速访问又减轻源站压力。其工作原理类似分级缓存：用户请求先查本地 CDN 节点，未命中则查询邻近节点，最终才回源站。需注意 CDN 失效时可能引发后端流量雪崩，需配合降级、限流等手段兜底。中小厂商通常采购云厂商 CDN 服务，自建 CDN 成本过高，仅适合超大型互联网企业。

2. 常见服务器架构对比

  • CS 架构（客户端-服务器）：适合低并发场景，早期应用较多，客户端需安装专用软件。
  • BS 架构（浏览器-服务器）：当前主流架构，用户通过浏览器以 HTTP 协议访问 Web 服务器，后端对接数据库，更适配现代动态网页需求。云端环境通常直接提供封装好的高可用与负载均衡能力，自建架构则需手动实现相关技术栈。

3. 负载均衡技术分层

  • 四层负载均衡：工作在传输层（OSI 第四层），代表方案为 LVS，基于 IP+端口转发流量，性能极高，但无法识别应用层内容。
  • 七层负载均衡：工作在应用层（OSI 第七层），代表方案为 HAProxy、Nginx，可基于 HTTP URL、Header 等内容做精细化调度（如动静分离、会话保持），对后端服务透明，无需配置 VIP。

📌 补充知识点：四层和七层不是替代关系，而是分层协作。生产环境常见架构：LVS（四层入口）→ HAProxy（七层分发）→ 后端集群，兼顾性能和灵活性。

二、LVS-DR 模式负载均衡

（1）ipvsadm 工具与基础命令

  1. ipvsadm 是 Linux 下用于管理 IPVS（IP Virtual Server，IP 虚拟服务器）的命令行工具，主要用于构建 LVS（Linux Virtual Server）负载均衡集群。它允许管理员配置和管理虚拟服务、真实服务器（后端节点）以及负载均衡策略。

    1）基础的查看命令

    2）添加 VIP 虚拟服务

    3）添加后端 RS 节点

    4）持久化保存

  3. LVS 有三种转发工作模式：

    • DR（Direct Routing）模式 -g：性能最优，调度器与后端服务器在同一网段，通过修改数据包的 MAC 地址实现转发，后端服务器需绑定 VIP。
    • NAT（Network Address Translation）模式 -m：性能较差，调度器与后端服务器不在同一网段，调度器需进行地址转换（SNAT），后端服务器需配置网关指向调度器。
    • TUN（IP Tunneling，IP 隧道）模式 -i：适用于跨网段场景（公网），通过 IP 隧道协议封装数据包，性能介于 DR 和 NAT 之间。

    📌 补充知识点：第四种模式 — FULLNAT
    除了 DR/NAT/TUN 三种经典模式外，还有 FULLNAT 模式（由阿里开源贡献）。它将请求和响应的源 IP、目标 IP 都做转换，使 RS 看不到客户端真实 IP，但部署更灵活（RS 可跨 VLAN），常用于大型云厂商内部。

  4. 常用的调度算法有四个：

    • rr 轮询：请求依次轮流分配，不考虑负载
    • wrr 加权轮询：根据权重分配请求
    • lc 最少连接；wlc 加权最少连接
    • sh 源地址哈希，实现会话保持

📌 补充知识点：排错时可用工具

  • tcpdump -i ens33 host 192.168.63.100 and port 80 → 抓包看三次握手
  • arp -a → 查看 ARP 缓存，确认 VIP 对应的 MAC 是调度器的
  • arp -d 192.168.63.100 → 清除指定 ARP 缓存条目
  • ipvsadm -Ln --stats → 查看流量统计，确认请求是否到达 RS

5. 一些疑问

1）我们什么时候用 /24, ens33，什么时候用 /32, lo 取决于我们的使用角色。

Director 调度器使用 ens33，ens33 时对外的物理网卡，需要让全网用户访问到 VIP。而 RealServer 后端服务器使用 VIP/32 dev lo，绑定在 lo 回环网卡，只让本机内部程序识别 VIP，禁止对外响应 VIP 的 ARP 请求，防止冲突。

2）arp_ignore 和 arp_announce 是什么

  • arp_ignore（收到别人 ARP 请求时，怎么应答）
    • 外部 ARP 询问 192.168.63.100 的 MAC 地址。请求包从 ens33 进来，但是 VIP 绑在 lo 上。此时 arp_ignore=1 → 拒绝回复 ARP，防止 RS 对外宣称 VIP。
  • arp_announce（本机对外发送 ARP 包时，源 IP 怎么选）
    • arp_announce=2 尽量使用和出接口网段匹配的 IP 作为 ARP 源地址。不会拿 lo 上的 VIP 当做源 IP 向外发送 ARP。能够防止 RS 主动向外广播【源 IP=VIP】的 ARP 报文。

📌 补充知识点：arp_ignore / arp_announce 取值含义

参数 取值 含义
arp_ignore 0 只要本机有这个 IP，任何网卡都应答
arp_ignore 1 只在接收请求的网卡上有该 IP 时才应答
arp_ignore 2 只应答本机所有网卡上配置的 IP（更严格）
arp_announce 0 允许使用任意 IP 作为 ARP 源地址
arp_announce 1 优先选择与目标 IP 同网段的地址
arp_announce 2 始终选择最匹配的地址（最严格，DR 模式推荐）

三、LVS-NAT 模式负载均衡（双网卡拓扑）

（1）原理

  1. VS/NAT 的优点是服务器可以运行任何支持 TCP/IP 的操作系统，它只需要一个 IP 地址配置在调度器上，服务器组可以用私有的 IP 地址。

  2. 缺点是它的伸缩能力有限，当服务器结点数目升到 20 时，调度器本身有可能成为系统的新瓶颈，因为在 VS/NAT 中请求和响应报文都需要通过负载调度器。

  3. 在这次实验里，调度器 VS 有双网卡：

    • ens32（外网）：192.168.10.100 【VIP，客户端访问入口】
    • ens33（内网）：192.168.63.131 【连接后端 RS，同时作为 RS 的默认网关】

    后端 RS 的网关仍在 192.168.63.x；测试的客户端在 192.168.10.x（与调度器外网同网段）

  4. 工作原理是：

    客户端访问虚拟 VIP，请求报文到达调度器；调度器将目标 IP 修改为后端真实服务器 RIP 并转发（DNAT）。后端服务器收到请求后，响应报文必须经由调度器回包，调度器再把源 IP 改回 VIP（SNAT）返回客户端。入站、出站所有流量都经过调度器完成地址转换，从而实现四层负载均衡。

📌 补充知识点：iptables 优先级 > IPVS
如果调度器上 iptables 的 INPUT 链拦截了 80 端口，请求到不了 LVS，负载均衡就会失效。排查时先 iptables -L -n 确认没有 DROP 规则，或干脆 systemctl stop firewalld 关闭防火墙再测试。

四、Keepalived + LVS-DR 高可用集群（主备调度器，解决调度器单点故障）

（1）原理

  1. 只用 ipvsadm 部署 LVS-DR 存在两大缺陷：一个是调度器单点故障（只有一台 server1 做调度器，一旦宕机，整个集群全部断网）；另一个是无后端健康检查（后端 server2/server3 的 httpd 宕机，LVS 依旧分发流量，用户访问报错）。

  2. Keepalived 是为 LVS 设计的高可用软件，基于 VRRP 虚拟路由冗余协议。

  3. 核心原理是：VRRP 协议与 VIP 漂移

    Keepalived 的高可用能力依赖 VRRP 协议，本质是让多台节点（主、备）共享一个”虚拟 IP（VIP）”，对外呈现为一个统一的服务入口，核心逻辑如下：

    1）角色划分：集群包含 1 个主节点（Master）和 1 个/多个备节点（Backup）。
    2）心跳检测：主节点定期向备节点发送 VRRP 通告报文（默认每 1 秒），证明自己”存活”。
    3）VIP 持有：正常情况下，主节点绑定 VIP 并对外提供服务，备节点仅监听心跳，不持有 VIP。
    4）故障切换：若备节点超过指定时间（默认 3 秒）未收到主节点心跳，判定主节点故障，备节点立即升级为新主节点，绑定 VIP 并接管服务，整个过程无需人工干预。

  4. 配置文件（以双节点为例）

    Keepalived 主配置文件默认路径为 /etc/keepalived/keepalived.conf，主、备节点配置差异主要在 state（角色）和 priority（优先级，数值越高越优先成为主节点）。

    • vrrp_strict 必须注释掉！否则 Keepalived 会自动添加 iptables 规则拦截流量，导致 curl 超时。

    📌 补充知识点：LVS 原生没有健康检测能力
    只用 ipvsadm 时，后端 RS 宕机了 LVS 照样分发流量，用户会访问报错。Keepalived 的 TCP_CHECK 解决了这个问题——它每隔 delay_loop 秒去探测 RS 的 80 端口，连不上就自动摘除，恢复后自动加回。
